# 연구 개요: 클라이언트 선택 압축은 서버 과제에 필요한 근거를 보존하는가

작성 2026-10-19 · 상태: 설계·모델 없는 검증 단계 (GPU 실험 미실시, 결과 없음)

표기: **[소스]** 공식 코드·데이터를 읽어 확인한 사실 · **[실행]** 이 저장소에서 모델 없이 실행해 확인한 것 · **[추론]** 소스 읽기로부터의 추론 · **[제안]** 설계 제안 · **[미확인]**

## 1. 질문

동일한 최종 서버 입력 예산(1,024 / 2,048 토큰)에서, 클라이언트 쪽 선택(SpecPC, LLMLingua-2, 문장 선택)이 서버(Qwen2.5-14B-Instruct)가 HotpotQA를 푸는 데 필요한 근거(개별 사실·연결 개체·조건)를 얼마나 남기는가? 손실이 생기는 조건은 무엇이고, 같은 예산 안에서 다른 선택으로 피할 수 있는가?

이 연구는 기존 멀티턴 라우팅 연구(`~/multiturn_routing_pilot`, `~/switchcost`)와 분리된 별도 저장소 `~/ctxcomp_pilot`에서 진행한다. 기존 저장소는 읽지도 수정하지도 않았다.

## 2. 먼저 밝혀 둘 중복

이 질문의 큰 틀(작은 모델이 큰 모델을 위해 입력을 고르는 것, 그 신호가 큰 모델의 필요와 얼마나 맞는지)은 **이미 선행연구에서 직접 다뤄졌다.** 새로운 분석이라는 주장은 보류한다. SpecPC 논문 텍스트에서 근거 단위 보존·실패 분류·동일 예산 복원을 찾지 못했다. 다만 그림, 다른 압축 연구(LongLLMLingua, RECOMP 등), 후속 연구는 확인하지 않았다.

"검색에서 못 찾음"은 "없음"이 아니다. 근거 단위 보존을 측정한 압축 연구, HotpotQA supporting facts로 압축 결과를 평가한 연구는 체계적으로 검색하지 않았다. 원고 단계 전에 별도 검색이 필요하다.

## 3. 지금까지의 관찰 (결과 아님)

1. **[실행] LongBench v1 hotpotqa(200문항)는 HotpotQA dev와 질문 문자열로 200/200 결합되고 정답도 200/200 일치한다.** 하지만 LongBench의 passage는 HotpotQA 첫 문단이 아니라 더 긴 (개정판) Wikipedia 문서 전체다. 자동 정렬(전체 463개 사실): exact 128 · high 183 · medium 114 · unmapped 38.
2. **[실행] 수작업 검증(규칙 v1, 서버 출력 없음, 주석자 = AI assistant).** dev 20문항(필수 근거 42개)과 진단 표본 15문항(필수 근거 31개)을 검증했다. 원본 HotpotQA 근거가 현재 LongBench 문맥에서도 정답을 지지하는지 문항별로 판정한 결과:
   - dev: 지지 17 · 질문 전제 충돌 1 · 모호(다른 정답도 지지) 1 · 부재에 의존 1
   - 진단: 지지 12 · 모호 2 · 정답 비지지(수치 개정) 1
   - 문항별 근거 수·판정은 `data/annotations/annotation_report.json`, 규칙은 `docs/06_annotation_rules.md`.
3. 아래 세 항목은 **서로 다른 문제**다.
   - **정답 문자열 부재**(표기 문제): gold 문자열이 문맥에 그대로 없는 문항이 자동 검사로 24/200개. 이 중에는 내용상 지지되는 문항이 있다(예: gold "43,000 marchers", 문맥 "43,000 demonstrators"). 지지되지 않는 문항도 있다(예: 2010 인구 → 2020 인구로 개정). 문자열 기반 EM·contains는 앞의 경우를 오답으로 셀 수 있다.
   - **원문 전체가 성능 상한이 아님**(입력 구성 문제): 원문 전체에는 방해 문맥과 상충 근거(1956/2004 동명 영화), 바뀐 전제(fourth → third album)가 함께 들어 있다. 그래서 압축 입력이 원문보다 나을 수 있다. 정답 문자열 유무와 무관하게 성립한다.
   - **문맥 길이 수용 가능성과 실제 GPU 실행 가능성도 별개다.** 최종 서버 입력 1,928–17,684토큰(중앙값 15,089)은 Qwen2.5-14B의 위치 한계(32,768) 안이라 잘라내지 않고 넣을 수 있다. 하지만 24GB 카드에서의 메모리·시간 실행 가능성은 아직 측정하지 않았다(`docs/04_preflight.md`). 2,048 이하는 1문항, 1,024 이하는 0문항이라 두 예산 모두 거의 모든 문항에서 실제 압축이 일어난다. 고정 부분(system·지시문·질문·템플릿)은 92–136토큰이다.
4. **[소스+실행]** SpecPC 공식 흐름은 마지막 64토큰만 보호한다. 그런데 context 뒤 접미부(지시문+질문+템플릿)가 64토큰을 넘는 문항이 11/200개 있어, 공식 흐름에서는 질문 앞부분이 잘릴 수 있다. system prompt는 보호되지 않는다.
5. **[실행]** SpecPC 선택 함수의 numpy 포팅은 tie가 없는 입력에서 공식 torch 함수와 정확히 일치한다. 공식 설정(max-pool 64)에서는 점수가 같은 구간이 길게 생겨, tie 처리 차이로 CPU torch와 선택 집합 일치율이 97.5–99.9%에 그친다. GPU에서 tie 순서는 다시 확인해야 한다. 포팅은 tie 연구·테스트 전용이고, GPU smoke와 실행은 공식 함수를 import해서 쓴다. 높은 일치율은 **재현 완료를 뜻하지 않는다**(draft 점수·GPU topk·토큰화는 smoke에서 처음 확인).
6. **[실행, 모델 없음]** dev 20문항에서 결정적 문장 선택 기준선의 근거 보존율(정렬 불확실성 포함, 서버 응답 없음):

| 방법 | 질문 접근 | B=1024 사실 보존 | B=1024 전체 사실 보존 문항 | B=2048 사실 보존 | B=2048 전체 사실 보존 문항 |
|---|---|---|---|---|---|
| BM25 문장 선택 | 있음 | 0.711 | 0.45 | 0.756 | 0.55 |
| 균등 위치 문장 선택 | 없음 | 0.044 | 0.00 | 0.111 | 0.00 |

위 표는 자동 정렬 기준이다. 수작업 requirement(대체 근거 포함) 기준으로 dev eligible 17문항에서 모든 필수 근거가 남은 문항: BM25 11/17(1024)·12/17(2048), 균등 0/17. 자동 정렬은 대체 근거를 고려하지 않고 정렬 오류도 있어 보존을 낮게 잡는다.

질문 접근 여부가 다른 두 방법의 차이이므로 압축기 능력 차이로 해석하면 안 된다. 서버 정답률과의 관계는 아직 측정하지 않았다.
